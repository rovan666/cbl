预算执行引擎：额度怎么分，超额怎么裁

目标：手推 allocate 的逐级压缩与最大余数法，讲清五种策略各自的适用场景，理解运行期断言与拒绝组装。

4.1 三步走

引擎（assemble_parts）就是计划书运行期语义的直接实现：

步骤做什么对应函数
1. 定 B本次可用额度：缺省 window × margin，调用方可调小assemble_parts 开头
2. 分额度Σcap 超 B 时按 low → medium → high 逐级压缩；must_keep 不参与allocate + _proportional
3. 裁内容读材料、估用量，超出有效额度的块执行声明的 overflow 策略STRATEGIES[...] 策略表

最后按声明顺序拼接（ⓓ），求值运行期断言。任何一步不行就走 reject()—— 拒绝组装也带审计记录，报告能说清死在哪一步。

4.2 互动演示：拖滑块，看逐级压缩

这是引擎核心算法的教学复刻（与 engine.py 的 allocate() 同一算法）。拖动滑块改变可用额度 B， 观察 low 先被压、压到 0 才动 medium、high 和 must_keep 雷打不动：

两个临界点
  • B = 7100（cap 总和）：以上足额分配，以下开始压缩；
  • B = 1800（must_keep 总额）：以下无解，拒绝组装——宁可什么都不送，也不丢过敏史。

最大余数法：同级压缩怎么取整

同级按 cap 等比例压缩会出现小数。先取整数部分，剩余名额按小数部分从大到小补——保证总和恰好等于目标值。 例：3 块各 100 分 200 → 66.7×3 → 取整 66×3=198，余 2 补给小数部分最大的两块 → 67、67、66。

4.3 五种超限策略对照

同一份材料（6 轮对话，上限 120 token），四种非 error 策略各自的真实产出：

策略适合什么材料思路
truncate_tail工具输出等"前面重要"的文本截断尾部，尽量停在句末（_soft_cut）
rerank_drop检索文档以本轮提问做 BM25 打分，整段丢弃相关度最低的，保持原顺序
summarize对话历史最近 keep_recent 轮留原文，早期压成摘要放前面；放不下就退化为滑窗
sliding_window只要最近的从最新往前整单位保留；一个都放不下时保留最新的末尾
errormust_keep（系统提示、过敏史）超额即拒绝组装——绝不静默裁剪

4.4 token 估算：宁多勿少 + 单调性

设计决定

缺省计数器是保守估算（中文每字 1.5、英文每 3 字符 1 个）：估多了只是少放一点，估少了会真的超窗。 它还对任意前缀单调不减——所以截断能二分查找"最长放得下的前缀"。需要精确时传 counter=tiktoken（可插拔，示例见 examples/plugin_demo.py）。

4.5 validate_plan：引擎不信任上游

JSON 计划是编译器与运行期之间的契约，但引擎不假设它一定来自本编译器（网页演示、手写、第三方生成都有可能）。 validate_plan() 在组装前检查结构与取值（必填键、枚举、类型），非法计划一次列出全部问题—— 和语义层复核约束③是同一个防御思路。

4.7 本课自测

1. 未用满的额度为什么不回流给别的块？

答辩高频题。主动承认代价，再讲设计理由，比硬撑"没代价"更专业。

2. 为什么 low 压到 0 才压 medium，而不是所有块按比例一起压？

B=6000 时 no_starvation 真的会报警告——示例就是这么设计的。

3. token 估算故意偏多的理由是什么？

保守方向的选择题：估多→少放（无害），估少→真超窗（有害）。

4. must_keep 块的实际用量超过 cap 会怎样？

这是整个语言的核心承诺：死保信息永远不会被悄悄丢掉。
思考题：rerank_drop 的已知局限是什么？

字面匹配认不出同义词：提问说"发烧"、资料写"发热"就对不上（示例里"咽拭子检测"段就被误丢）。 改进方向：同义词表或向量检索——策略表是可插拔的，新增策略不改主流程。

测试体系：65 个用例怎么把守质量

目标：讲清三层测试、正反例表驱动、快照测试、变异检查，以及 CI 怎么自动跑它们。

6.1 三层测试

层内容文件
前端词法/语法错误的反例：行列号、期望符号、错误恢复一次报全tests/run_tests.py 前半
语义错误目录 16 项逐项正反例 + 覆盖率自检tests/run_tests.py 的 PAIRS
端到端真实示例 + 真实材料跑引擎，快照逐字比对tests/engine_cases.py、webui_cases.py

入口统一：python tests/run_tests.py，当前 65 个用例。CI（GitHub Actions）在每次 push/PR 时 用 Python 3.10 和 3.12 各跑一遍。

6.2 正反例表驱动（语义层的测试设计）

错误目录里每个编号配一对：正例（必须编译通过且不含该编号）和反例（必须报出该编号）。 16 个编号 = 16 对，写在一张 PAIRS 表里，测试脚本自动生成用例。

闭环

case_catalog_covered 反向检查：目录里的每一项都必须在 PAIRS 里有正反例。 新增检查忘了写测试？测试自己先失败。这就是"测试测试"——防止质量机制本身退化。

6.3 快照测试：冻结行为

引擎的裁剪行为（哪段被丢、摘要多少字）被完整存进 tests/snapshots/，每次测试逐字比对。 任何人改了裁剪逻辑，测试立刻红——行为变化必须经过人的确认：

CBL_UPDATE_SNAPSHOTS=1 python tests/run_tests.py   # 确认是预期变化后，接受新快照
单元测试快照测试
断言什么具体性质（如"used ≤ effective"）整个输出逐字不变
优点失败时指向明确任何意外变化都藏不住
代价性质要想得全预期内的变化也要人确认一次

6.4 变异检查：测试真的在把关吗

前几课你已经做过三次了：删 _is 的类型检查、删 check_source、改压缩次序—— 每次都预期测试失败。如果改了代码测试还全绿，说明测试有洞。这是审阅代码时最有价值的思路之一。

6.5 网页层的测试

  • webui_cases.py 会在随机端口起真实 HTTP 服务，逐个接口发真实请求；
  • 越权路径（/static/../cli.py）必须 404；超大请求体只看请求头就返回 413；
  • XSS 测试：把 </script><script>alert(1)</script> 塞进提问，导出报告验证转义。

6.6 动手实验

实验 · 完整走一遍"改代码"流程

① 故意把 report.py 里"完整保留"改成"完整" → ② 跑测试，看 case_snapshot_reports 红掉并打印实际输出 → ③ 如果这是预期变化，CBL_UPDATE_SNAPSHOTS=1 接受 → ④ 再跑一遍全绿 → ⑤ git checkout . 还原。这就是本项目改代码的标准流程。

6.7 本课自测

1. 快照测试和单元测试的关系是？

快照的代价是任何变化都要人确认——所以它只用于"审计报告"这种输出物，不用于内部函数。

2. 新增一条语义检查后，忘了写正反例测试，会发生什么？

测试体系自己守卫自己的完备性，这是表驱动设计在测试侧的镜像。

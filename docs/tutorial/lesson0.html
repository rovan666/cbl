0.2 流水线：六个阶段

CBL 系统按编译原理的经典流水线组织。每个阶段的产物，就是下一个阶段的输入——这句话是整个课程的骨架：

.cbl 源文件 ──词法──▶ Token 列表 ──语法──▶ AST ──语义──▶ 诊断列表
      （lexer.py）        （parser.py）      （semantic.py）│ 全部通过
                                                            ▼
                                            JSON 组装计划（ir.py 生成）
                                                            │
            上下文材料 + 本轮提问 + 可用额度 B ──引擎（engine.py）┘
                                                            │
                          最终 Prompt + 审计记录 ──报告（report.py / webui.py）
关键划分

上半段是编译期：只看你声明的数字与结构，不碰真实材料； 下半段是运行期：拿真实材料执行预算。这就是为什么换个材料不用重新"编译"， 而改了 cap 必须重新编译。

0.3 每层的产物到底长什么样

阶段产物数据结构通俗理解
词法Token 列表Token(kind, value, line, col)源码的"单词表"
语法ASTProgram{window, blocks[], rules[]}源码的"句子结构树"
语义诊断列表Diagnostic(level, line, msg, code)"意思通不通"的检查单
IRJSON 计划普通 dict编译期给运行期的"交接单"
引擎Prompt + 审计str + dict真正干活的产出

0.4 动手：把六个阶段各跑一遍

动手实验（必做）

打开终端，cd D:\学习用的\编译原理\DSL\cbl，依次：

① 看源文件——这就是"语言"本身：

type examples\medical_assistant.cbl

② 看编译产物（编译期的终点）：

python -m cbl check examples/medical_assistant.cbl

注意两个现象，先记住，第 2、3 课解释：
· chat_history 的 source_kind 是 "ident"（而其它块是 "string"）
· 没写 overflow 的块，计划里被补上了缺省值

③ 看运行结果（运行期的终点），跑两次对比：

python -m cbl run examples/medical_assistant.cbl
python -m cbl run examples/medical_assistant.cbl --budget 6000

第二次额度少了 1100：tool_output 被整块舍弃、chat_history 被压缩—— 源文件一个字没改，只是运行参数变了。这就是"一次声明、两处生效"。

④ 打开预算实验台（第 4 课的主练场）：

python -m cbl serve

拖动"可用额度"滑块，看五个块此消彼长；地址后加 ?budget=6000 直达某个场景。

0.5 本课自测

1. 把过敏史材料文件改长了一些，需要重新编译 .cbl 源文件吗？

编译期的产物（JSON 计划）只包含声明的结构与数字；材料长度是运行期才知道的，由引擎按预算策略处理。

2. 为什么语义检查放在语法分析之后、IR 生成之前？

分层各司其职：词法管"单词对不对"，语法管"句子结构对不对"，语义管"意思通不通"，IR 只给通过检查的程序生成。

3. "编译期"和"运行期"的分界线在哪两个阶段之间？

JSON 计划之前全是编译期（静态、不碰材料），之后是运行期（拿真实材料执行）。
思考题：如果让你给 CBL 加一种新块（比如"知识图谱查询结果"），从声明到出现在最终 Prompt，要经过哪些阶段？

词法（不用改，名字走标识符规则）→ 语法（不用改，就是普通 block）→ 语义（自动被九条约束检查）→ IR（自动多一个块条目）→ 引擎（按 priority/overflow 参与分配与裁剪）→ 报告（自动出现在审计里）。 一个新块零改动穿越全流水线——这就是声明式语言的力量，也是第 3 课"表驱动"的回报。

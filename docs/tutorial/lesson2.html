语法分析：把 Token 组装成 AST

目标：能手推每条产生式对应的函数调用链，讲清 LL(1)、缺省值填入、相对 cap 折算、恐慌模式错误恢复。

2.1 语法分析在干什么

生活类比

词法分析分出了"词"，语法分析要理解"句子结构"：block notes { ... } 里， notes 是块名、花括号里是条目——就像"主语 + 谓语 + 宾语"。输出是一棵抽象语法树（AST）： 程序的结构化表示，后续所有阶段都在这棵树上工作。

CBL 的完整文法（EBNF）写在 parser.py 文件开头的注释里，总共十条左右产生式。最核心的四条：

program    = { windowDecl | blockDecl | ruleDecl } ;
blockDecl  = "block" ident "{" { blockItem } "}" ;
capItem    = "cap" ":" operand ";" ;        (* 与断言右值共用 operand *)
operand    = int | int "%" | "window" "*" number ;

2.2 递归下降：一条产生式 = 一个函数

实现方式是手写递归下降：parse_program 调用 parse_block， parse_block 调用 parse_operand……函数之间的调用关系就是文法的结构。三个基础工具函数撑起一切：

函数作用一句话
peek()看当前 Token，不消费"下一个是什么？"
advance()吃掉当前 Token"确认了，吞掉"
expect(value)断言当前是指定终结符，否则报错"这里必须是分号！"
文法是 LL(1) 的

每个选择点只看一个 Token 就能决定走哪条分支：顶层看是不是 window/block/rule； 块内看条目关键字；operand 看是 INT 还是 window，INT 后面再看有没有 %。 不需要回溯，没有左递归——所以递归下降能胜任，不需要 ANTLR 这类生成器。

2.4 终结符匹配的一个真实漏洞（答辩素材）

_is() 不只比较字面值，还要求 Token 的类型是 KEYWORD 或 SYMBOL：

tok.value == value and tok.kind in ("KEYWORD", "SYMBOL")

为什么？因为字符串 ";" 的字面值和分号一模一样。历史上只比较值时， window 8000 ";" 能蒙混过关、"cap": 100 能被当成 cap 条目。 修复后字符串再也不能冒充终结符，有专门的测试守着（case_strings_cannot_impersonate_terminals）。

答辩素材

这个 bug 说明：值相同 ≠ 同一个终结符，词法类别本身就是语法的一部分。被问"词法和语法的界限"时可以用它回答。

2.5 相对 cap：cap 与断言右值共用 operand

这是 11 月新加的文法变化：capItem 从 "cap" ":" int ";" 变成了 "cap" ":" operand ";"，于是两种新写法合法了：

cap: 40% ;              # 窗口的 40%
cap: window * 0.4 ;     # 同上，另一种写法

好处：换窗口尺寸时不用重算各块额度。实现上有个微妙的点：解析 block 时 window 可能还没声明 （顺序自由），所以 parser 先把相对 cap 记下来，整条程序解析完、window 已知后再由 _resolve_caps 折算成绝对值（四舍五入）。AST 下游只看到整数——语义检查、IR、引擎、快照全部零改动。 真实编译结果：

源码写法IR 里的 cap（真实编译器输出）
cap: 40% ;（window 8000）…
cap: window * 0.4 ;（window 8000）…

2.6 恐慌模式错误恢复：一次报出全部语法错误

旧版 parser 遇到第一个语法错误就抛异常停止。现在的版本：出错后跳到下一个同步点继续分析， 全部错误收进 ParseErrors 一次报出。同步点规则：

层级同步点实现
顶层（声明之间）消费掉 ; 或 } 后停；遇到下一条声明开头（window/block/rule）或 EOF 直接停_sync_top()
块内（条目之间）消费掉 ; 后停；遇到 }（留给外层消费）或 EOF 直接停_sync_item()

2.8 本课自测

1. 递归下降的核心思想是什么？

parse_program / parse_block / parse_operand 的调用关系就是文法的层级结构。

2. 为什么缺省值（如 must_keep 块的 overflow=error）在语法分析阶段就填入，而不是留给引擎？

这就是"IR 是交接单"的含义——交接单上不能有需要对方猜的隐含规则。

3. cap: 40% 是什么时候折算成绝对值的？

解析 block 时 window 可能还没声明，所以先记下来，最后统一折算。下游只看到整数。

4. 恐慌模式恢复里，块内同步点为什么不消费 }？

同步点的设计原则：跳过坏的部分，但不能吃掉属于上层结构的 token。
思考题：错误恢复会不会把"连带错误"也报出来，误导用户？

会，这是恐慌模式的已知代价（比如块头坏了，块内条目可能被连锁报错）。CBL 的缓解：顶层完整性检查 （"缺少 window"之类）只在没有任何语法错误时才做，避免在恢复出的残局上报误导性的次生错误。

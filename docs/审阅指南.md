## 1. 徐同帅：词法分析与语法分析

### 阅读顺序

1. [tokens.py](https://github.com/rovan666/cbl/blob/50b4276/cbl/tokens.py)：21 个关键字、界符表。**先记住 Token 只有四个字段**。
2. [lexer.py `tokenize`](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L21)：一个 `while` 循环里按首字符分 7 个分支——
   [空白](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L41)、
   [注释](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L46)、
   [字符串](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L54)、
   [数字](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L67)、
   [标识符/关键字](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L84)、
   [双字符运算符](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L96)、
   [单字符界符](https://github.com/rovan666/cbl/blob/50b4276/cbl/lexer.py#L104)。
3. [parser.py 基础工具](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L59)：`_is` / `expect` / `expect_kind`——所有产生式都靠这三个函数"吃" Token。
4. 产生式函数，**对照 EBNF 读**（文件开头的注释就是文法）：
   [`parse_program`](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L78) →
   [`parse_window`](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L98) →
   [`parse_block`](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L112) →
   [`parse_rule`](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L149) →
   [`parse_operand`](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L171) →
   [`_choice`](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L189)。

### 设计决定（答辩要讲得出理由）

- **手写递归下降，不用 ANTLR**：文法只有十条左右产生式；每个产生式对应一个函数，报错能精确到"第几行、期望什么、实际读到什么"，比生成器的默认报错更适合教学（计划书问题一）。
- **文法是 LL(1) 的**：每个选择点只看下一个 Token 就能决定走哪条分支，不需要回溯——顶层看 `window/block/rule`，块内看条目关键字，`operand` 看是 `INT` 还是 `window`，`INT` 后面再看有没有 `%`。文法里没有左递归。
- **最长匹配**：数字分支读完整数后，只有"点后面还是数字"才继续读成 FLOAT；`<=` 必须先于 `<` 判断（双字符分支在单字符之前）。
- **终结符匹配同时检查类型**（`_is`）：这是在 [`50b4276`](https://github.com/rovan666/cbl/commit/50b4276) 修掉的真实漏洞——之前只比较值，于是 `window 8000 ";"` 里的字符串 `";"` 被当成分号、`"cap": 100` 被当成条目都能通过。**这是一个很好的答辩素材**：说明"值相同 ≠ 同一个终结符"，词法类别本身就是语法的一部分。
- **报错写清楚读到的是什么**：字符串会标明"字符串"；缺分号报在**缺的那一行**（上一个 Token 所在行），并注明实际读到的 Token 在哪行。
- **缺省值在语法分析时填入**：`priority=medium`、`overflow=truncate_tail`，但 must_keep 块未写 overflow 时缺省为 `error`（[parser.py#L144](https://github.com/rovan666/cbl/blob/50b4276/cbl/parser.py#L144)，配合语义约束⑨）。

### 可能被问的问题

| 问题 | 回答要点 |
|---|---|
| 为什么不用 ANTLR / yacc？ | 文法小；手写能控制报错质量；课程要求锻炼前端能力。代价是改文法要手改函数。 |
| 你的文法是 LL(1) 吗？怎么说明？ | 是。逐个选择点说明：各分支的 FIRST 集互不相交（见上面"设计决定"第二条），所以看一个 Token 就能定分支；没有左递归。 |
| 词法分析器对应什么自动机？ | 手写的确定有限自动机：循环开头按当前字符跳到某个"状态"（7 个分支），在状态内累积字符直到不能再接受为止（最长匹配），然后产出 Token。 |
| 能一次报出多个语法错误吗？ | 不能，遇到第一个语法错误就停（抛异常）。可以做"恐慌模式"恢复：出错后跳到下一个 `;` 或 `}` 继续。**语义错误则一次全部报出**（见第 2 节）。 |
| `"high"` 和 `high` 有什么区别？ | 前者是 STRING 类 Token，后者是 KEYWORD 类；枚举值必须是关键字。讲一下 `50b4276` 那个修复。 |
| 关键字能当块名吗？ | 不能，21 个关键字都是保留字，例如 `block error { ... }` 会报"期望块名（标识符）"。 |

### 已知局限

- 字符串不支持转义、不能跨行（按计划书正规式的规定）。
- 没有语法错误恢复，一次只报第一个语法错误。
- 关键字保留，块名不能叫 `error`、`high` 等。

### 设计决定

- **错误目录 + 表驱动**（计划书问题四）：新增一条检查只需三步——目录里加一行、写一个函数挂进 `CHECKS`、`PAIRS` 里加一对正反例。漏写测试会被 `case_catalog_covered` 拦下。
- **属性文法体现在哪**：`total_reserved`（各块 cap 之和）是**综合属性**，由各 block 的 cap 自底向上汇总到 Program；`window`、`margin` 从根节点向下传给各项检查使用，起**继承属性**的作用。约束①②⑦都建立在这些属性之上。
- **一次报出全部语义错误**：九个检查都跑完再汇总，按行号排序——用户一次能改完，不用"改一个、编译一次"。
- **编译期 vs 运行期断言**：只依赖 cap 与 window 的断言（`total_reserved`）编译期就能求值；依赖运行期数据的（`every_block_min_tokens`，即压缩后的有效额度）留给引擎。失败时都按规则自己的 `on_violation` 定级别（R702 的级别因此不固定）。
- **约束③为什么在语法已经拦住后还要查**：语法分析器保证源码里的枚举合法，但 AST 也可能被程序直接构造（测试、以后的网页编辑器），语义层再复核一次，防御性检查。
- **约束⑨（must_keep 的 overflow 只能是 error）**：从语言层面兑现"死保信息不被任何策略裁剪"的承诺。
- **IR 里缺省值全部显式写出**：引擎不需要知道 CBL 的缺省规则；`source_kind` 告诉引擎是读文件还是取内置来源；`metric`/`op` 单独给出，引擎不必再解析断言字符串。

### 可能被问的问题

| 问题 | 回答要点 |
|---|---|
| 属性文法体现在哪？ | 综合属性 Σcap 自底向上，继承属性 window/margin 自顶向下；约束是定义在属性上的谓词。 |
| 为什么不在语法分析时顺便检查？ | 分层：语法管"句子结构对不对"，语义管"意思说不说得通"。比如 Σcap 超窗，必须等所有 block 都读完才能判断。 |
| 九条约束怎么保证实现正确？ | 每个错误编号一对正反例 + 覆盖率自检 + 变异检查（删掉检查函数，测试必须失败）。 |
| R702 为什么有时是错误、有时是警告？ | 规则级别由用户写的 `on_violation` 决定；内置约束①是固定的错误，规则机制让用户写出比它更严格（或更宽松提示）的纪律。 |
| 为什么要 JSON 中间表示，不直接解释 AST？ | 编译器与引擎解耦，可以各自替换；JSON 可存档、可 diff、任何语言都能读。 |
| 符号表怎么做的？ | block 与 rule 共用一张表（一个 dict），CBL 没有嵌套作用域，一层就够。 |

## 3. 杨晨：预算执行引擎

### 阅读顺序

   [truncate_tail](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L214)、
   [sliding_window](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L221)、

   [rerank_drop](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L256)、

4. 基础设施：[`estimate_tokens`](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L46) → [`_fit_prefix`（二分）](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L69) → [`_soft_cut`](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L93)；
   [`bm25_scores`](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L299)、[`rule_summary`](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L335)；
   [`eval_rules`](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L366)；
   [`load_material`（含路径沙箱）](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L152)。

### 设计决定

- **可用额度 B 与压缩次序**（计划书运行期语义 ⓑ）：B 缺省为 window×margin，可调小；Σcap 超过 B 时按 low → medium → high **逐级**压缩，一级压到 0 才动下一级；must_keep 不参与压缩。
- **最大余数法**：同级按 cap 等比例分配时先取整数部分，剩下的名额按小数部分从大到小补，保证各块之和**恰好**等于目标值，不多不少（例：3 块各 100 分 200 → 67、67、66）。
- **策略统一签名、放进表里**：主流程只写 `STRATEGIES[b["overflow"]](...)`，新增策略不改主流程——和语义检查的表驱动是同一种思路。
- **token 保守估算**（ⓔ）：中文每字 1.5、英文每 3 字符 1 个，宁多勿少——估多了只是少放一点，估少了会真的超窗。估算函数对任意前缀**单调不减**，所以截断时可以二分查找"最长能放下的前缀"。
- **计数器、摘要器可插拔**：`assemble(counter=..., summarizer=...)`，可以换成 tiktoken 或大模型摘要。
- **截断尽量停在句末**（`_soft_cut`：在前缀最后 20% 里找句号）。
- **rerank_drop = BM25 + 中文二字组合**：零依赖、不需要分词器。试过再加单字作检索词，结果无关段落得分反而升高（噪声大于收益），已否决。
- **拒绝组装带审计记录**（`AssemblyError.audit`）：报告能说清楚是哪一步、为什么失败。
- **字符串来源限制在材料目录内**：网页允许编辑源码，不限制的话 `source: "../../任意文件"` 能读出电脑上任意文件。

```bash
python -m cbl run examples/medical_assistant.cbl --budget 1700   # 低于死保总额 1800：拒绝组装
```

1. 把 [engine.py#L21](https://github.com/rovan666/cbl/blob/50b4276/cbl/engine.py#L21) 的压缩次序改成 `("high", "medium", "low")`，跑测试——5 个用例失败（单元、端到端、快照、网页、HTTP 接口各层都拦住了）。

### 可能被问的问题

| 问题 | 回答要点 |
|---|---|
| 未用满的额度为什么不回流给别的块？ | 可预测、可审计：每块拿多少只取决于声明，不取决于别的块这次材料多不多（ⓑ）。代价是可能有浪费，由用户调 cap 解决。 |
| 为什么 low 压到 0 才压 medium，而不是大家按比例一起压？ | 优先级的语义就是"严格先后"；按比例压会让高优先级也受损。担心低优先级被饿死，就写 `no_starvation` 规则兜底——示例里 B=6000 时它会报警告。 |
| token 估算不准怎么办？ | 故意偏多，保证"引擎认为放得下，真实分词器下也放得下"；需要精确就传 `counter`。编译期只看 cap 数字，与分词器无关。 |
| rerank_drop 的局限？ | 字面匹配，认不出同义词：提问说"发烧"、资料写"发热"就对不上，示例里"咽拭子检测"一段就被误丢。改进：同义词表或向量检索（策略可插拔）。 |
| 摘要是怎么做的？ | 规则式：每轮用户/助手各取首个有信息量的句子（≥8 字），再补与提问共享 ≥2 个检索词的句子；超长时停在句末。可换成大模型摘要。 |
| 性能如何？拖滑块为什么不卡？ | 示例一次编译 + 组装约 12 ms（只编译前端约 0.2 ms）；截断用二分，复杂度 O(n log n)。 |
| must_keep 的内容超过 cap 怎么办？ | 拒绝组装并报错（ⓐ），绝不静默裁剪——约束⑨保证它的策略必为 error。 |

### 已知局限

- token 是估算值，不是真实分词结果。
- rerank 只做字面匹配；规则式摘要质量有限。
- rerank 以段落为单位，只有剩一段仍超额时才截断它。
- 块之间的分隔符 `\n\n` 不计入额度（开销极小，由 margin 预留覆盖）。

### 设计决定

- **审计记录以 JSON 为主格式**，文本、HTML、网页都只是它的不同视图。
- **网页和 HTML 报告共用一个渲染器**（report.js）：两边视觉永远一致，只维护一份代码；HTML 报告把样式、渲染器、数据全部内嵌，单文件离线可看。
- **防 XSS 两道关**：渲染器只用 DOM API 和 `textContent` 写文本，从不拼接 HTML 字符串（材料内容不可信）；内嵌的 JSON 把 `< > &` 转成 `\u` 形式，材料里即使有 `</script>` 也截断不了脚本。
- **单位状态怎么判定**：看这段/这轮原文是否出现在最终文本里（保留）、只出现首尾片段（部分保留）、位于保留原文之前且有摘要（并入摘要），否则丢弃。**曾经的 bug**：摘要会引用早期轮次的首句，这些轮次被误判成"部分保留"，页面显示"保留 7/8 轮"，实际只保留了 4 轮——修法是"并入摘要"的判断必须先于"部分保留"，并加了回归测试。
- **拖动不乱序**：每次请求带序号，只认最新响应，旧请求用 `AbortController` 取消。
- **快照测试**（计划书问题五 ③）：把审计报告文本存进 `tests/snapshots/`，每次逐字比对——引擎有人改了裁剪行为会立刻暴露。
- **演示服务的安全**：缺省只监听 127.0.0.1；静态文件名不能含路径；请求体超过 256KB 只看请求头就返回 413。

### 动手验证

1. 在 [report.py#L56](https://github.com/rovan666/cbl/blob/50b4276/cbl/report.py#L56) 的 `if` 下面加一行 `act = act.replace("完整保留", "完整")`，跑测试——`case_snapshot_reports` 失败并打印实际输出。如果这个改动是你想要的，执行
   `CBL_UPDATE_SNAPSHOTS=1 python tests/run_tests.py` 接受新快照（PowerShell 里先 `$env:CBL_UPDATE_SNAPSHOTS=1`）。
2. `python -m cbl serve`，地址后加 `?budget=6000`、`?budget=1700` 看三种场景；改坏源码看诊断和行号标红；点"导出 HTML 审计报告"。
3. XSS 实验：在"本轮用户提问"里输入 `</script><script>alert(1)</script>`，导出报告再打开——不会弹窗，提问原样显示在页眉。

### 可能被问的问题

| 问题 | 回答要点 |
|---|---|
| 为什么用 JS 渲染，不用 Python 直接拼 HTML？ | 网页要实时交互，本来就得用 JS 渲染；让 HTML 报告复用同一个渲染器，就不用维护两份视觉代码。 |
| 怎么防止材料里的恶意内容注入页面？ | `textContent` + JSON 转义两道关；有专门的测试（`case_html_report_embed_safe`）。 |
| 快照测试和普通单元测试有什么区别？ | 单元测试断言具体性质；快照测试"冻结"整个输出，任何变化都要人确认，适合防止行为被悄悄改变。 |
| 拖滑块会不会卡、会不会显示错乱？ | 一次请求约 12 ms；序号 + 取消旧请求，保证画面只显示最新结果。 |
| 局域网模式安全吗？ | 同一 Wi-Fi 的人都能访问、能编辑源码；但来源路径被限制在材料目录内，读不到其他文件。它定位是演示工具，没有登录鉴权。 |

### 已知局限

- 单位状态是基于子串的启发式判断，材料里如果有完全重复的段落可能误判。
- 演示服务没有鉴权（`--lan` 时同网段可访问）。
- HTML 报告需要开启 JavaScript 才能显示（原始数据仍在页面源码里）。

## 5. 任何人都可能被问的问题

| 问题 | 回答要点 |
|---|---|
| CBL 和直接在 Python 里写配置有什么区别？ | 静态检查（编译期发现超窗、死保无解、拼写错误）、可审计（每次组装有报告）、与模型和框架解耦（计划书领域需求①~⑤）。 |

| 演示时间只有五分钟，怎么演？ | 建议顺序：缺省 7200（四种策略都触发，展开 chat_history 看摘要）→ 压缩场景 6000（低优先级被整块舍弃、规则报警告）→ 无解 1700（拒绝组装）→ 在源码里把 allergy_notes 的 overflow 改成 truncate_tail（约束⑨当场报错）。 |
